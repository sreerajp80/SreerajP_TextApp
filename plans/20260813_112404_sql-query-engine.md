## 1. What the issue is

Today the app can filter a CSV by keyword, sort it by several columns, and query
JSON with JSONPath. None of that can **group**, **aggregate**, or **join**. A
user who wants "total sales per region, highest first" or "the rows in this CSV
whose id also appears in that JSON array" has to leave the phone.

The roadmap asks for a real SQL surface over open CSV files and JSON arrays:
`SELECT`, `WHERE`, `GROUP BY`, `ORDER BY`, `JOIN`, fully offline.

## 2. The approach

### 2.1 No new dependency

The roadmap entry suggests `sqflite_common_ffi`. That package is for **desktop
and test hosts** — it is already in the project, but only as a `dev_dependency`.
On Android the plain `sqflite` package (already a runtime dependency) opens an
**in-memory** SQLite database with `inMemoryDatabasePath`. That is all this
feature needs, so **no new package is added** (CLAUDE.md §11).

The engine takes a `DatabaseFactory` argument. The app passes the default
(Android) factory; tests pass `databaseFactoryFfi`, exactly as
`test/core/index/search_index_repository_test.dart` already does.

### 2.2 How data gets into SQLite

The document buffer is copied into a throwaway in-memory database each time the
query screen opens:

1. The open document becomes a `SqlDataset` — a plain list of columns and string
   rows. CSV comes from `CsvTable`; JSON comes from the existing `JsonTable`,
   which already flattens an array of objects into columns.
2. Each column gets a SQLite type from the app's existing `inferColumnType`:
   `number`/`currency` → `REAL`, `boolean` → `INTEGER` (0/1), everything else →
   `TEXT`. That is what makes `WHERE amount > 100` compare as a number instead
   of as text, and it reuses code that is already tested.
3. Rows are inserted in one batch inside a transaction. A blank cell becomes
   `NULL`, never `0` or `''`, so `AVG` and `COUNT` do not lie.
4. The original column name is kept as the SQL column name (quoted). Blank names
   become `column_1`, `column_2`…; a repeated name gets `_2`, `_3` appended. The
   screen shows the final names so the user always knows what to type.

The database is created fresh, held only for the life of the screen, and closed
on dispose. It is **never** the app's own `text_data.db`.

### 2.3 Joins across open documents

The current document is always loaded as the table `data`. The user can add any
**other open CSV or JSON tab** as an extra table (named from its file name,
sanitised, e.g. `users_csv`), which is what makes `JOIN` useful. Extra tables are
read from the live session for that tab; a tab whose session is not loaded yet is
loaded and awaited with a timeout, and a tab that fails to load is reported
rather than silently skipped.

### 2.4 Safety

Even though the database is a temporary in-memory copy, the typed SQL is treated
as untrusted input (CLAUDE.md §3.4):

- Only **one** statement is allowed, and it must start with `SELECT` or `WITH`.
- `ATTACH`, `DETACH`, `PRAGMA`, `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`,
  `CREATE`, `REPLACE`, `VACUUM`, `load_extension`, `readfile` and `writefile` are
  refused. `ATTACH` is the important one: without this block a query could reach
  the app's real database file on disk.
- The check ignores text inside string literals and comments, so a query like
  `WHERE note = 'delete me'` still runs.
- A SQLite error is caught and shown as a friendly message with the engine's own
  text kept as detail. Nothing crashes (CLAUDE.md §3.4).
- The query text, the result rows, and the file content are **never logged**
  (CLAUDE.md §8).

### 2.5 Limits (stated in the UI, not hidden)

| Limit | Value | Why |
| :--- | :--- | :--- |
| Rows loaded per table | 200,000 | Keeps the copy inside a phone's memory. Above it, the first 200,000 rows load and the screen says so. |
| Result rows shown | 5,000 | The grid stays responsive; a truncation note appears. |
| Query cancel | not offered | SQLite runs the query on sqflite's background thread and cannot be interrupted part-way. A row cap is the honest protection; the UI shows a spinner and says a heavy query can take a moment. |

### 2.6 What the user can do with a result

- Read it in a scrollable grid (the same `two_dimensional_scrollables` engine the
  CSV and JSON grids use).
- Copy the result as CSV to the clipboard.
- Save the result as a new CSV file through the system file picker
  (`SafService.createDocument` — scoped storage only, CLAUDE.md §3.3).

Opening the result as a new in-app tab is **out of scope**: every tab assumes a
real SAF URI, which is the same architectural limit already recorded for
memory-only notes in the roadmap.

## 5. Risks and honest limits

- **The query runs over a copy.** Editing the document after opening the query
  screen does not change the loaded tables; a "Reload data" button re-copies. The
  screen states this.
- **Memory.** A 200,000-row table copied into SQLite plus the Dart buffer is real
  memory pressure on a small device. The cap and the note are the mitigation.
- **JSON nested values.** `JsonTable` already shows a nested object as `{ 3 }`.
  Those cells load as that same short text, so a query cannot reach inside a
  nested object. Flattening nested JSON is a separate, larger job.
- **Manual check before release.** Unit tests run on the host through FFI. A run
  on a real Android device must confirm the device's own SQLite behaves the same,
  matching the rule already applied to LAN sync and AirQR (CLAUDE.md §10).
