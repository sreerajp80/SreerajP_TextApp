# Plan — A clear way to quit edit mode, and auto-save gaps

**Status:** completed

## 1. The issue

Once a document tab goes into edit mode, there is no clear or reliable way out.

1. **Hard to find.** The only exit is the small toolbar toggle. While editing it shows an
   **eye** icon (`Icons.visibility_outlined`). People read an eye as "this is a preview",
   not as "tap here to stop editing". There is no text label and no other exit.
2. **Saving does not leave edit mode.** After a successful save the tab stays in edit
   mode, so the keyboard and the editing tools stay on screen.
3. **Back button does nothing.** There is no `PopScope` anywhere in the app, so the
   Android back button cannot be used to leave edit mode.
Going Home and tapping the same file brings the tab back still in edit mode. That is
**kept as it is** (decided while reviewing this plan): the tab should return exactly as the
user left it. Once (1)–(3) give a clear way out, this is no longer a problem.

The same pattern exists in TXT, Markdown, JSON and XML. (CSV has no edit mode — it has
table/raw views — so CSV is not part of this change.)

## 2. The plan for the fix

### A. Make the exit control obvious

In the four toolbars, when the document is being edited, show an explicit **exit** icon
(`Icons.edit_off_outlined`) with the tooltip "Exit edit mode" instead of the eye icon.
When not editing it keeps the pencil icon with "Edit mode". This keeps one button but
makes its meaning clear in both states.

### B. Android back leaves edit mode first, and asks about unsaved changes

Wrap the tabs workspace body in a `PopScope`. When the active tab is in edit mode, the
back press does not leave the screen — it exits edit mode instead:

- **Tab has no unsaved edits** (`tab.isDirty == false`) → leave edit mode straight away,
  no dialog.
- **Tab has unsaved edits** → show the **existing** unsaved-changes dialog
  (`showUnsavedChangesDialog`, `lib/shell/tabs/unsaved_changes_dialog.dart`), the same one
  the tab-close guard already uses, so back and close behave alike:
  - **Save** → save the file; on success leave edit mode. A failed save keeps the tab in
    edit mode and shows the reason (edits are never lost — CLAUDE.md §3.6). A read-only
    file that cannot be overwritten falls back to "save as a copy", exactly as the close
    guard does today.
  - **Save as a copy** → same, through `saveAsCopy()`.
  - **Discard** → throw the unsaved edits away with `reloadFromDisk()` (all five sessions
    already have it) and also drop the saved draft, so the draft banner does not offer the
    discarded text back. Then leave edit mode.
  - **Cancel** → stay in edit mode and change nothing.
- If it is not in edit mode, back behaves exactly as it does today.

The per-format save lookup already exists as `_saverFor` in `tabs_workspace.dart`; it will
be widened slightly so the back handler can also reach `reloadFromDisk` and
`discardDraft`, and reused instead of writing a second copy.

### C. Return to view mode after a save

Add an editor setting **"Leave edit mode after saving"**, default **on**, and apply it in
the four direct-save paths. A user who likes to keep editing after a save can turn it off
in Settings → Editor.

### D. One place that knows "is this tab editing?"

The back handler in (B) must not learn the internals of five formats, so add two small
helpers in `lib/formats/format_dispatch.dart`:

- `bool isTabEditing(WidgetRef ref, DocumentTab tab)`
- `void exitTabEditMode(WidgetRef ref, DocumentTab tab)`

Both switch on `detectFormat(tab)` and use each format's session manager `peek(tab.id)`, so
they never build a session that does not exist yet. Each format maps its own mode enum
(`TabViewMode`, `MdMode`, `JsonViewMode`, `XmlViewMode`) to "editing / not editing" and to
its own default view mode. The toolbars in (A) and the save path in (C) use the same
helpers, so the mapping lives in exactly one file.

### E. Auto-save gaps

**First, what auto-save is here.** It is *draft* auto-save for crash recovery, not saving
to the real file. Every few seconds (`editor.autosave_seconds`, default 5, `0` = off) the
`AutoSaver` writes the editor text to a private draft file keyed to the document's
fingerprint (`lib/core/editor/draft_store.dart`). On the next open the tab offers
"Restore / Discard". A real save clears the draft. The real file is only ever written when
the user saves.

**It is wired up and it works.** All five sessions build an `AutoSaver` after their load
finishes and start it on the settings interval; all five discard the draft on a real save.
`flutter test test/core/editor/draft_store_test.dart` passes (6 tests), including
"a kill mid-edit is recovered on the next open". So this is not a broken feature. But three
real gaps make it lose more work than it should:

**E1 — Nothing is flushed when the app leaves the foreground.** The editor surfaces already
watch the app lifecycle, but on `inactive` / `paused` / `hidden` they only call
`persistPosition()` (for example `lib/formats/txt/txt_editor_surface.dart:66-75`) — they do
not flush the draft. Android can kill a paused app at any moment, so the user loses
everything typed since the last tick, even though the app got a clean warning it was going
away. With the interval set to its 600-second maximum that is a lot of work.
**Fix:** expose `flushDraft()` on each session (an `await _autoSaver?.tick()`) and call it
from the same lifecycle hook that already saves the position. CSV has no lifecycle observer
at all in `lib/formats/csv/`, so it gets one, which also fixes its reading position.

**E2 — A failed auto-save is silently dropped.** `AutoSaver.start` does
`Timer.periodic(interval, (_) => tick())` and throws the returned `Future` away
(`draft_store.dart:157-160`). If the draft write fails — disk full, index error — the
error becomes an unhandled async error that nobody sees, and the user keeps typing thinking
their work is protected. That is exactly the silent failure CLAUDE.md §3.6 and §9 forbid.
**Fix:** catch inside `tick()`, keep the last error on the `AutoSaver`, and let the session
surface a quiet "Auto-save is not working" note in the editor. The tick keeps retrying;
`_lastSaved` is only updated after a write that actually succeeded.

**E3 — Changing the interval in Settings does not reach open tabs.** `autoSaveInterval` is
read once when the session is built (`sessionFor` in each `*_session_manager.dart`). Turn
auto-save off, or make it faster, and every already-open tab keeps its old timer until it
is closed and reopened.
**Fix:** have the session managers watch `editorSettingsProvider` and push the new interval
into live sessions with a `setAutoSaveInterval(Duration)` that restarts (or stops) the
timer.

Not changing: `dispose()` stops the timer without a last tick. That looks risky but is not
— the retention policy in `tabs_workspace.dart` never releases a dirty tab, and a real tab
close already goes through the unsaved-changes prompt. Adding a flush there would also
fight the "Discard" choice, which wants the draft gone. Left as it is, on purpose.

### Not doing: resetting the tab when reopened from Home

Tapping a file on Home that is already open and being edited will **keep the tab in edit
mode**, exactly as the user left it. No reset, no prompt. `open_file_action.dart` is
therefore unchanged.

## 4. Checks after the change

- `dart format lib test`
- `flutter analyze` — must be zero issues
- `flutter test`
- Manual: open a TXT file, edit, save → back in view mode; press back while editing with
  no changes → view mode, no dialog; press back with unsaved changes → the save prompt
  appears and each of its four buttons behaves as described in (B); go Home and tap a file
  that is being edited → the tab comes back still in edit mode, unchanged.
- Manual auto-save: type, send the app to the background, kill it from the recents screen,
  reopen → the draft banner offers everything typed, not just up to the last tick. Change
  the interval in Settings with a tab already open → the open tab follows the new interval.

## 5. Out of scope

- CSV (no edit mode).
- Any change to the read-only lock, or to draft recovery.
- The unsaved-changes dialog itself: it is reused as it is, not redesigned.
- Resetting a tab's mode when the file is reopened from Home.
