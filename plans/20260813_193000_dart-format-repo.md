# Run `dart format` across our own Dart code

**Status:** completed

## What the issue is

Our Dart code is not formatter-clean. `dart format` would rewrite:

- **186 of 259 files** in `lib/`
- **83 of 114 files** in `test/`

That is **269 files** in total.

The reason is not sloppy code. Dart 3.7 shipped a **new formatter style** (often called the
"tall style"). It mainly changes how long argument lists, constructor calls, and chained
calls are wrapped, and it moves trailing commas around. The codebase was written under the
old style, so almost every file with a multi-line call differs.

There is **no formatter config** in `pubspec.yaml` or `analysis_options.yaml` today, so the
formatter uses its defaults (80-column page width, style tied to the package language
version, which is Dart 3.12 here).

## Why do it now

The previous change (`prefer_initializing_formals`) left a few constructors with small
cosmetic leftovers like `})  : _now = ...` (two spaces before the colon). Formatting fixes
those and stops the drift from growing.

## The plan

1. Run `dart format lib/ test/`.
2. Run `flutter analyze` — expect **0 issues**, same as now.
3. Run `flutter test` — expect **all 831 tests to pass**, same as now.
4. Spot-check the diff in a few security-sensitive files
   (`lib/core/storage/key_value_store.dart`, `lib/sync/sync_crypto.dart`,
   `lib/sync/sync_transport.dart`, `lib/sync/sync_provider.dart`) to confirm only
   whitespace and line breaks moved.
5. Write the change log.

## Files to be changed

269 files under `lib/` and `test/`. I am not listing them one by one — it is "most of the
codebase". The change is **whitespace and line breaks only**. `dart format` does not change
what the code does; it only reprints the same parsed code.

## Important: what I will NOT format

- **`third_party/`** — vendored `re_editor` source. It is other people's code, it is already
  excluded from analysis in `analysis_options.yaml`, and reformatting it would make future
  updates from upstream painful to merge. `dart format .` would have touched 323 files
  because it includes this folder; scoping to `lib/ test/` keeps it out.
- I will **not** add a `formatter:` / `page_width` setting to `pubspec.yaml`. That is a
  separate style decision. Say the word if you want a width other than the default 80.

## Risk and the honest downside

**Risk to behaviour: essentially zero.** The formatter reprints the same code, and
`flutter analyze` plus the full test suite will confirm it.

**The real cost is git history.** A 269-file whitespace commit means:
- `git blame` on those lines will point at this commit instead of the real author/change.
  `git blame -w` (ignore whitespace) still works, and the commit can later be added to a
  `.git-blame-ignore-revs` file if you want blame to skip it permanently.
- Any in-flight branch or stash will likely conflict when merged.

Because of that second point, this is best done as **its own commit, with nothing else in
it**, and best done when you do not have other work in progress. Right now the working tree
also has the earlier `prefer_initializing_formals` changes and some doc edits uncommitted —
worth committing those first so the format change lands clean and separate.
